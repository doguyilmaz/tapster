## 1. Release

In tapster setup, open **Projects** and click the project under **In the hub**. Once the release workflow on its
default branch is tapster's, the **Releases** step offers a release. Above the button it says what the hub's last check
found about its App:

<Image src={status} alt="The project's sheet: every step is done and the Releases step shows the commit to tag, the version v0.2.2 and a Release button." />

- **Commit**: the latest commit of the default branch on GitHub, with its date. This is what gets the tag.
- **Version**: the next patch after the highest version tag on GitHub, such as `v0.2.2` after `v0.2.1`. A project
  without one starts at `v0.1.0`. You can type another version as long as it is higher.

Click **Release**. tapster creates the tag on GitHub with your own sign-in, at exactly the commit it showed. If the
branch moved in between or the tag exists already, it refuses and says why. It never tags the clone on your computer,
which can be behind or on another branch.

The same release from a terminal is one command. The sheet shows it with the commit filled in, under
**Or tag it from a terminal**:

```sh
gh api --method POST repos/you/my-tool/git/refs -f ref=refs/tags/v0.1.0 -f sha="$(gh api repos/you/my-tool/commits/main --jq .sha)"
```

## 2. The project opens a draft

The project's release workflow builds the archives, writes `checksums.txt`, attests the files and opens a **draft**
release. The sheet follows it: the workflow's run, then the draft, then the hub's publish, each with a link. You can
also watch it on the project's **Actions** tab.

:::tip[You should see]{icon="approve-check-circle"}
A draft release named `v0.1.0` with the archives and `checksums.txt`. It is not public yet.
:::

## 3. The hub signs and publishes it

The hub looks for drafts every 10 minutes. With the [doorbell](/guides/doorbell/) it starts right away. Follow it on
the hub's **Actions** tab, workflow **tapster**:

<Steps>

1. **check** finds the draft and checks where it came from. The tag must exist. The draft and every file must come from
   the project's workflow or from you.
2. **sign** downloads the files and compares each one with `checksums.txt` and its build attestation. It signs the macOS
   binaries, sends them to Apple for notarization and waits for Apple's answer. Then it replaces the archives in the
   draft and publishes the release.
3. **attest** attests the signed files.
4. **render** writes `Casks/my-tool.rb` (and `bucket/my-tool.json` for Windows builds) to the hub.

</Steps>

A fifth job, **report**, runs only when something needs you. It opens the issue `tapster: the hub needs attention` in
the hub and closes it once all is well.

:::caution[tapster waits here]{icon="clock"}
Apple's notarization usually answers within a few minutes. tapster waits up to 30 minutes for it.
:::

:::tip[You should see]{icon="approve-check-circle"}
The release `v0.1.0` is published on the project. The hub has a new commit, `my-tool v0.1.0`, with the cask.
:::

## 4. Install it

Anyone can now install the tool from your tap:

```sh
brew tap you/tap
brew trust you/tap
brew install you/tap/my-tool
```

Homebrew loads casks only from taps you trust, so `brew trust` comes once per tap.

Check that macOS sees your signature:

```sh
codesign -dv --verbose=2 "$(command -v my-tool)" 2>&1 | grep Authority
```

:::tip[You should see]{icon="approve-check-circle"}
`Authority=Developer ID Application: Your Name (TEAMID)` on the first line.
:::

## If the hub does not publish

The hub writes the reason at the top of the draft's release notes. The project's sheet in tapster setup shows it under
**Releases** too. See [Troubleshooting](/reference/troubleshooting/#on-a-draft)
for each reason.

Then check the whole setup:

```sh
cd homebrew-tap
bunx @doguyilmaz/tapster doctor
```
